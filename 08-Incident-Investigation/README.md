# 08 — Incident Investigation

This chapter defines a repeatable analyst workflow for investigating alerts generated by the Wazuh lab. The objective is to move from an alert to a defensible assessment supported by endpoint, network, and rule-level evidence.

> **Evidence standard:** distinguish what the telemetry proves, what it suggests, and what remains unverified. A rule match is an investigation lead, not automatic proof of compromise.

## 1. Investigation workflow

1. **Triage the alert**
   - Record the alert timestamp, rule ID, rule level, description, agent ID/name, and manager.
   - Identify the detection source and relevant fields, such as username, source/destination IP, process, file path, Windows Event ID, or Suricata signature.
   - Check whether the activity is expected, authorized, and consistent with the lab scenario.

2. **Validate the underlying event**
   - Inspect the alert's `full_log`, `decoder`, and `data` fields when present.
   - Compare the alert with the endpoint's original event or log entry.
   - Confirm that the decoded fields used by the rule represent the actual event. Do not rely on the alert description alone.
   - If the event did not trigger an alert, check whether the raw event was collected and whether archive logging is enabled.

3. **Scope the activity**
   - Identify the affected endpoint, account, source and destination addresses, process, file, and service.
   - Search for related events on the same endpoint and, where possible, other endpoints.
   - Check for repeated attempts, successful authentication after failures, privilege changes, account/group changes, persistence, and follow-on activity.

4. **Build a timeline**
   - Put related events in chronological order.
   - Record the timezone for every timestamp and normalize the working timeline to UTC where possible.
   - Distinguish the time recorded by the source from the time the Wazuh manager received or processed the event. Delayed agent delivery can affect apparent ordering.
   - Include the event source and evidence reference for each timeline entry.

5. **Assess impact and confidence**
   - Determine whether authentication succeeded, privilege was elevated, an account or group changed, persistence was created, or a file/log was modified.
   - State whether the activity is confirmed malicious, suspicious but unconfirmed, benign/authorized, or inconclusive.
   - Explain the evidence supporting the assessment and identify telemetry gaps.

6. **Recommend response**
   - Recommend proportionate containment, eradication, and recovery actions.
   - Record whether an action was manual, simulated, or executed by Wazuh Active Response.
   - Do not describe a recommended or configured action as successfully executed unless the result was verified.

7. **Close out**
   - Record the conclusion, evidence references, response outcome, limitations, and lessons learned.
   - Identify rule tuning or additional telemetry that would improve detection quality.

## 2. Wazuh evidence sources

| Source | Use during investigation |
|---|---|
| `/var/ossec/logs/alerts/alerts.json` | Structured records for events that matched rules and met the configured alert threshold. |
| `/var/ossec/logs/alerts/alerts.log` | Human-readable alert records. |
| Wazuh Dashboard — Security Events | Search, filter, and review indexed alerts. |
| `/var/ossec/logs/archives/archives.json` | Raw collected events, including events that did not trigger alerts, when archive logging is enabled. |
| Endpoint-native logs | Validate the original activity, for example Linux `auth.log`, Windows Security/Sysmon logs, or Suricata `eve.json`. |
| Wazuh rule and decoder configuration | Confirm the logic and fields that produced the alert. |

**Important:** Wazuh does not enable all-event archive logging by default in every deployment configuration. The `archives.json` file is available for this investigation workflow only when the appropriate archive collection/output settings are configured. Do not assume that a missing alert means the event never occurred.

## 3. Investigation scenarios

Use the relevant chapter for the detection logic and lab-specific configuration. The scenarios below are investigation paths, not claims that every scenario has already been independently validated.

- **SSH authentication:** repeated failures followed by a successful login; compare source IP, username, event order, and authentication result.
- **Privilege escalation:** sudo activity and root-shell attempts; verify the actual command and resulting privilege context.
- **Linux account and persistence changes:** new local accounts, SSH `authorized_keys` modifications, and cron changes; validate the account/file state on the endpoint.
- **Authentication log tampering:** investigate FIM events affecting `/var/log/auth.log`; distinguish modification, truncation, and deletion using the original event details.
- **Windows RDP:** correlate failed logons (Event ID 4625) and successful logons (Event ID 4624, Logon Type 10); verify account, source address, and sequence.
- **Windows process activity:** inspect process creation and Sysmon telemetry where configured; validate executable path, command line, parent process, and user.
- **Active Directory changes:** investigate account creation/deletion, account disablement, and security-group membership changes; validate the corresponding Windows Security events and affected object.
- **Network activity:** correlate Suricata alerts with endpoint and firewall telemetry; confirm direction, protocol, signature, and whether the observed traffic reached the target service.

## 4. Minimum case record

For every documented investigation, capture:

- Case/reference ID and investigation date.
- Alert timestamp and timezone, rule ID, level, description, and alert JSON reference.
- Affected agent ID/name, hostname, operating system, and relevant asset context.
- Detection source, decoder, and relevant decoded fields.
- Relevant user/account, source/destination addresses, process, file path, or event ID.
- Related events and a timestamped timeline.
- Analyst assessment, confidence, and supporting evidence.
- Containment/remediation recommendation and actual action taken.
- Validation result, false-positive considerations, telemetry gaps, and remaining uncertainty.

## 5. Validation and documentation rules

- Use `/var/ossec/bin/wazuh-logtest` to test how a sample event is decoded and which rules match. A logtest result validates rule processing for that sample; it does not by itself prove that the live endpoint collected or generated the event.
- For an end-to-end validation, retain evidence of the activity on the endpoint, the collected event, and the corresponding Wazuh alert or archive record.
- Preserve relevant raw event content and timestamps. Protect passwords and SSH private keys by replacing them with `<REDACTED>`. Hash values that are part of controlled demonstrations may remain visible, as agreed for this portfolio.
- Preserve IP addresses, MAC addresses, hostnames, usernames, timestamps, rule IDs, and other technical details.
- Never publish passwords, credentials, or private-key material. Demonstration hash values may remain visible when they are intentionally included as technical evidence.
- Label screenshots and exported logs with the scenario, source host, and capture date. Keep evidence references consistent between the investigation notes and the relevant project chapter.
- Do not fabricate missing events, alert outcomes, response results, or analyst conclusions.
