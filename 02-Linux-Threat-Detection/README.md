# 02 — Linux Threat Detection

This project documents a controlled Linux attack-and-detection lab using Wazuh agents, Linux authentication logs, custom rules, and File Integrity Monitoring.

## Lab objectives

Detect and investigate behaviors associated with:

1. SSH authentication failures and a subsequent successful login.
2. Privilege escalation through `sudo`.
3. Local account creation.
4. SSH key-based persistence through `authorized_keys`.
5. Authentication log tampering.
6. Scheduled-task persistence through cron.

## Telemetry and centralized collection

The lab notes configure the Linux agent group to collect:

```xml
<agent_config os="Linux">
  <localfile>
    <location>/var/log/auth.log</location>
    <log_format>syslog</log_format>
  </localfile>
</agent_config>
```

The notes also configure FIM for selected account and SSH files. See [04 — File Integrity Monitoring](../04-File-Integrity-Monitoring/README.md).

Ensure the target distribution actually writes authentication events to the configured path. Some distributions use different logging services or paths.

## Scenario 1 — SSH brute force and successful authentication

Detailed project documentation: [SSH Brute-Force Detection and Successful-Login Correlation](SSH-Brute-Force/README.md).

Detailed project documentation: [SSH Brute-Force Detection and Successful-Login Correlation](SSH-Brute-Force/README.md).

**Objective:** identify repeated failed SSH authentication attempts and investigate a subsequent successful login.

**Lab simulation:** use a dedicated test account and a controlled password list from the isolated attacker VM. Do not run password-guessing tools against systems outside the lab.

**Detection approach:**
- Collect the Linux authentication log.
- Identify the exact built-in Wazuh rule IDs generated by failed and successful SSH authentication events.
- Correlate repeated failures using a bounded time window.
- Where supported by the decoded event, constrain correlation to the same source IP.
- Investigate whether a successful login followed the failures.

The notes include a draft rule using SIDs 5712 and 5715 and custom rule ID 100010. These SIDs and the proposed parent/child relationship must be verified against actual alerts from the installed Wazuh release before use. Do not assume rule IDs are identical across releases or event formats.

**MITRE ATT&CK:** T1110.001 — Password Guessing.

## Scenario 2 — Privilege escalation

**Objective:** identify suspicious elevation to a root shell.

The notes use `sudo su -` and `sudo -i` as simulation examples and propose a rule based on SID 5402 with custom rule ID 100011.

A command-string match alone is not a complete privilege-escalation detection. Validate the decoded fields, parent rule, target user, and event source using real events and `wazuh-logtest`. Prefer structured audit data where available.

**MITRE ATT&CK:** T1548.003 — Sudo and Sudo Caching.

## Scenario 3 — Account and SSH-key persistence

**Objective:** detect creation of a local account and modification of SSH authorized keys.

The notes describe creating a dedicated lab account and adding a test public key to its `authorized_keys` file. Use a disposable account and a generated lab-only key. Never publish private keys or reuse personal SSH keys.

Detection sources:
- Authentication or audit logs for account-management activity.
- FIM alerts for changes to SSH authorized-key files.
- Contextual review of the affected user, file path, timestamp, and process/account that made the change.

The notes propose custom rule ID 100012 and base SID 5902 for account creation. Verify that SID against the actual event before relying on it. The FIM event should be validated independently; an account-creation alert does not prove that SSH persistence was established.

**MITRE ATT&CK:**
- T1136.001 — Create Account: Local Account.
- T1098.004 — Account Manipulation: SSH Authorized Keys.

## Scenario 4 — Authentication log tampering

**Objective:** detect unauthorized truncation, deletion, or modification of an authentication log.

The notes monitor `/var/log/auth.log` and propose custom rule ID 100013 based on the `syscheck` group.

Validate which FIM event fields and rule groups are emitted by the installed version. A file-change alert should be correlated with the actor, time, host, and related authentication activity. Do not assume every modification means the log was cleared.

**MITRE ATT&CK:** T1070.001 — Clear Linux or Mac System Logs.

## Scenario 5 — Cron persistence

**Objective:** identify suspicious changes to scheduled tasks.

The notes monitor `/var/spool/cron` and record system log messages from the `crontab` utility, including edit, replace, and list operations. They also contain a draft decoder and rule ID 100003.

Important validation points:
- Confirm the target distribution's cron implementation and log format.
- Confirm whether the relevant event is emitted by `crontab`, `cron`, auditd, or FIM.
- Test the decoder against representative raw log lines with `wazuh-logtest`.
- Confirm that the rule fires on a change event, not merely on a list/read operation.
- Keep any reverse-connection or persistence simulation strictly inside an isolated, disposable lab; do not include live callback commands or real endpoint addresses in public documentation.

**MITRE ATT&CK:** T1053.003 — Scheduled Task/Job: Cron.

## Rule development and validation

The custom rule IDs in the notes (100003 and 100010–100013) are proposed lab identifiers, not guaranteed production-ready rules. Before publishing a rule as validated:

1. Capture a representative raw event.
2. Run it through `/var/ossec/bin/wazuh-logtest`.
3. Confirm decoder output and the base rule ID.
4. Confirm the custom rule ID and expected fields.
5. Generate the event on the endpoint.
6. Confirm the alert arrives in the dashboard.
7. Record the alert JSON with secrets and personal data removed.

See [06 — Custom Detection Rules](../06-Custom-Detection-Rules/README.md).
